Lab Activity 6.1: Stateful Restaurant Order Agent & Dynamic Tool Calling Engine 
Business Scenario 
Perpetual Bistro, a high-volume campus dining facility, is prototyping an automated table-side digital ordering system. 
Customers place complex orders, request modifications (e.g., "Extra cheese, no onions, make it vegetarian"), ask about 
menu ingredients, and add/remove items dynamically before confirming their order. 
The bistro needs a local, zero-cloud conversational engine that maintains active table session memory, checks real-
time menu availability from an SQLite database, dynamically updates the customer's tab, and prevents hallucinated 
menu items. 
Lab Description 
Working in pairs (Driver & Navigator), you will build a Python CLI application powered by Ollama (qwen2.5) and SQLite. 
The application acts as a stateful order intake agent that maintains session state using an FSM pattern. 
Step-by-Step Implementation: 
1. Database Setup (restaurant.db): Initialize SQLite tables for menu_items (id, name, category, price, stock_qty, 
allergens), table_sessions (session_id, table_no, status), and order_line_items (session_id, item_id, quantity, 
special_instructions). 
2. Tool Definition & Function Binding: Define Python functions that the LLM can invoke: 
o get_menu_by_category(category) 
o check_item_allergen(item_id, allergen) 
o add_item_to_order(session_id, item_name, qty, instructions) 
o view_current_order(session_id) 
3. Conversational FSM Loop: Construct a Python state loop containing 5 distinct states: 
o STATE_GREETING: Welcome customer, capture table number. 
o STATE_TAKING_ORDER: Handle queries, recommend items, and bind tool calls to add/modify items. 
o STATE_REVIEW: Present current itemized tab with calculated totals for customer verification. 
o STATE_CONFIRMED: Commit transactional changes to restaurant.db, update stock levels, and output 
order receipt.

1. The Core Analogy: Driving a Vehicle
In a road trip or rally race:
• The Driver controls the physical steering wheel, pedals, and gear shift. They 
focus on tactical execution—staying in the lane, avoiding immediate 
hazards, and managing current mechanics.
• The Navigator holds the map or GPS, reads terrain notes, and watches for 
upcoming turns. They focus on strategic direction—ensuring the team gets 
to the destination without taking wrong turns or running out of fuel.

Why This Separation of Concerns Is Pedagogically Powerful
• Eliminates the "Pass-the-Keyboard" Chaos: Without defined roles, two 
developers sharing one computer often end up either arguing over the 
keyboard or having one passive person zoning out.
• Dual-Scope Problem Solving: It allows two programmers to solve a single 
problem at two different levels of abstraction simultaneously (micro-
implementation + macro-architecture).
• Continuous Code Review: The Navigator acts as a real-time code reviewer, 
catching typos, logic errors, and missing guardrails before the code is ever 
committed or executed.
• Active Role Rotation: Roles are swapped frequently (e.g., every 30–60 
minutes or at major project milestones) so both partners develop both 
hands-on coding skills and high-level architectural thinking.
